# 用户 Telegram Bot

## 角色与入口

使用独立用户 Bot Token，管理员继续使用既有管理员 Bot；禁止两个接收循环共用 Token。侧边栏新增 Telegram，包含消息、日志、设置三个页签。既有管理 Bot 指令保持兼容，新增管理员回复桥接。用户 Bot 只接受私聊，不在群聊泄露订阅凭据。

用户购买后由管理员创建客户端及入站。管理员可发送订阅链接和 Bot 账号，用户向 Bot 发送链接绑定；也可在 Telegram 管理页选择客户端生成限时、一次性绑定码，发送给用户。绑定码只存摘要，默认 30 分钟有效。绑定只比对客户端核心订阅标识：消息文本包含某客户端的 sub_id 即视为该客户端的凭据，不校验协议、域名、端口或路径，也不访问用户提供的 URL；文本同时命中多个客户端时拒绝歧义绑定。用户 Bot 使用独立绑定表，不将既有可多客户端的 tg_id 字段作为身份凭据。

绑定关系双向唯一：一个 Telegram 账号只绑定一个客户端，一个客户端只绑定一个 Telegram 账号。绑定采用数据库事务和唯一约束，不能覆盖其他人的绑定；换绑前先解绑。绑定码与订阅链接在消息和日志中保留原文，供管理员核对；Bot Token 不写入普通日志，接口错误中的 Token 与代理凭据仍脱敏。管理员可查看绑定状态、生成绑定码及解除绑定。

## 用户命令

提供 /start、/notifications（重新获取全部通知）、/subscription（获取链接）、/reset（确认后重置链接）、/usage（剩余流量、剩余天数）、/bind、/unbind（确认后解绑），使用 Telegram 原生 / 指令提示，不发送底部快捷回复键盘；普通指令响应携带 remove_keyboard 清除旧键盘，重置与解绑的消息内确认按钮保留。重置只改本客户端订阅标识，不改代理凭据和客户端身份；沿用客户端 Service/Runtime 更新流程。禁用或过期状态仍可查询和联系管理员，不允许操作其他客户端。非命令文本和附件作为咨询消息。「开启匿名聊天」默认关闭；关闭时，仅当前绑定有效客户端的账号可转发咨询，未绑定账号只处理指令和绑定凭据，普通文本及附件保留排障记录但不转发、不计待回复未读。开启后允许未绑定用户咨询。

## 绑定尝试风控

同一 Telegram 账号 10 分钟内最多进行 30 次绑定尝试，覆盖 /bind 带参、/start 带绑定码、直接发送绑定码或订阅链接，以及 /bind 后的待绑定输入。超限时立即拉黑该账号：黑名单持久化，此后该账号的全部消息与回调一律忽略，待发送的队列消息取消；触发当次回复限制提示并记录日志，不记录后续被忽略的消息。解除拉黑需管理员清理黑名单记录。尝试计数为进程内 10 分钟滑动窗口，接收器重载不清零，进程重启后清零；黑名单不受重启影响。

## 双向聊天

所有用户消息进入持久化会话，网页可分页查看会话与消息，主动向指定会话发文字或附件并回复特定消息。支持文本、图片、文件、视频、音频、语音和贴纸等 Telegram 消息；附件存 Telegram file_id/元数据，不长期保存二进制。网页可通过受管理员鉴权的下载代理查看附件，不向浏览器暴露 Token。

用户非命令消息转发到已配置的管理员 Chat ID；管理员在管理员 Bot 中回复该条转发消息时，以数据库保存的 Bot/Chat/Message 映射定位用户，严禁从转发文本猜测收件人。跨 Bot 的 file_id 不可互用，附件桥接需从源 Bot 下载再经目标 Bot 上传；受 Telegram 下载限制时保留原消息元数据、明确记录附件转发失败，不伪装为成功。网页与 Bot 的发送结果、失败和回复关联统一展示。

## 定向通知与可靠性

已绑定用户可使用 /notifications 主动重新收取全部当前可见的已发布通知，每次调用均重新入队，按通知顺序发送；不因之前已收过而跳过。未绑定用户先提示绑定；草稿、已撤回和其他客户端通知不返回。响应显示本次通知数量，无通知时明确提示；发送沿用持久化队列、限速及版本/受众校验。

新用户首次成功建立绑定时，在绑定事务内将该客户端当前可见的全部已发布通知加入发送队列，按 sort_index、id 顺序发送，不受发布到节点选项影响。客户端与当前用户分组以并集参与匹配，重叠命中只发送一次；草稿、撤回和无关通知排除。重复提交同一已存在绑定不重发；解绑后重新建立绑定会重新补发当前通知。发送失败沿用持久队列重试，队列写入失败则整个绑定事务回滚。

管理员发布已实现的订阅通知时，在同一数据库事务内按通知客户端与分组的并集范围加入发送队列，仅包含当时绑定且仍匹配的用户；不广播全部用户。发送前重新检查通知版本、发布状态和绑定关系，撤回、换绑、删除客户端或旧版本排队消息不再发送。咨询与回复优先于批量通知队列；发送有速率控制、超时和有界重试，进程重启后保留待发消息；失败在消息和日志页面可见。

## 设置与日志

设置包含启用、用户 Token（只写、显示已配置状态）、公开订阅地址前缀、管理员消息转发、开启匿名聊天和保留天数。移除清除 Token 选项，输入框留空保留已保存 Token，填写新值替换。关闭匿名聊天后，排队但尚未转发的未绑定用户咨询也取消；操作失败时不扩大转发权限。网络代理/API 地址沿用现有 Telegram 配置。保存后重载用户 Bot，不要求重启面板。Token 不进入普通设置视图、导出接口示例或错误 URL。

用户 Bot 的全部收发消息、命令、发送尝试和运行错误入库；消息与日志保留原文，不替换占位符。日志分页、可筛选，并可按天数清理或全部清理；自动按设置天数保留，消息历史也提供独立的保留天数及清理操作。清理不删除绑定、不改变待发送及发送中的消息，UI 说明删除历史不可恢复。恢复管理员 Bot 回复仍需要的映射不能先于关联消息被自动清除。

数据库新增模型必须同步注册 allModels/migrationModels。管理接口沿用管理员权限与 CSRF，节点同步令牌不可读写聊天和 Token。用户 Bot 启停与面板生命周期绑定，重载先取消并等待旧接收循环结束，禁止重复轮询。不得为验证向真实用户发送测试消息。

## 订阅详情、节点名和短时消息

`/subscription` 返回「你的订阅链接为」、订阅地址、可选「MIXED连接信息为」及各可用 mixed 的名称、HTTP/SOCKS5连接地址和账号密码。提示 Clash/Singbox 用户使用 https://sublink.osur.eu，并明确消息30秒后删除。确认重置订阅后的新链接也使用相同格式和有效期。mixed 复用订阅展示页查询、节点分享地址策略及客户端/入站配额过滤。

`/nodes` 需要绑定，按当前订阅生成结果顺序，仅返回真实节点名，包含手动 mixed；无地址、端口、凭据、通知占位或流量提示节点。复用既有订阅生成服务及外部链接，不另写节点归属查询。名称缺失使用协议名兜底，名称中的换行合并为空格；不合并相同名字的不同节点。无节点时明确提示。加入 Telegram 原生 `/` 菜单，保留该名称以防自定义指令覆盖；如旧配置已有 nodes 自定义项，内置优先并从自定义菜单排除。

订阅敏感回复按Telegram消息长度拆分，所有分片在各自发送成功30秒后请求删除。删除队列独立持久化、按 Bot 身份隔离，并由受生命周期管理的单个后台 worker 批量读取到期任务。重启后继续；Token 变更后不误删另一 Bot 的同号消息。失败有界退避重试并记录具体错误，已不存在视为删除成功。受Telegram API/网络限制，删除可能延迟或失败，管理日志仍按原保留策略保存。

## 邀请码管理与深链接检查

邀请码生成后在 Telegram 管理页固定列表展示，管理员可随时重新查看、复制、轮转和吊销。保留一次性、30分钟有效规则；保留当前记录的已使用/已吊销/已过期状态，不因关闭弹窗或刷新丢失。每客户端保留最新一份，轮转使旧码立即失效。绑定成功原子标记已使用；只有有效且未使用、未吊销的码可绑定。旧版只保存哈希的码无法恢复原文，界面提示轮转。邀请码原文只经管理员无缓存接口返回，不进入 SQL 日志。

用户通过 `https://t.me/<bot>?start=bind_...` 点击开始时，无需另发 /bind；服务端收到完整 /start 参数后立即绑定。裸 /start 不猜测目标客户端，明确提示缺少绑定参数并记录诊断事件。检查覆盖生成两次后，旧码拒绝、新码通过完整 Update/Message/command 路径自动绑定。

## 重置订阅的凭据撤销

Bot 确认 /reset 后，同时轮转订阅标识和所有附加入站使用的客户端级代理身份；复用现有客户端更新、停用和 Runtime 分发，不改变配额、流量、到期、分组或绑定。先停用旧身份再逐入站更新，成功后恢复原启用状态；失败保持停用并记录真实错误，不把部分更新报告为成功。WireGuard/AmneziaWG 保留各入站分配地址并轮转密钥；Shadowsocks 使用对应 cipher 要求的密钥长度；不支持客户端级认证的入站明确拒绝安全重置。子节点更新沿用主子 Runtime 流程。已有长连接的终止能力取决于核心协议实现，旧凭据必须不能再建立新连接。

不同 Shadowsocks cipher 或 MTProto 域名的入站凭据可与共享客户端字段不同，订阅生成按入站设置批量投影相应认证字段；其他协议保留共享身份。安全重置额外确认远端 Runtime 应用，离线不报告完成。恢复前所有已附加节点必须确认新凭据处于停用状态。

安全更新通过现有客户端更新 RPC 的 `applyImmediate=1` 请求即时应用确认；子节点仅在保存配置并将正在运行的核心对齐后返回 `obj.applied=true`，手动停止的核心保持停止。主控要求明确确认标记，旧版子节点无法确认时报告需要升级，不将其普通保存响应视为运行态完成。
