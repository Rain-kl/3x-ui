# 发布流水线耗时优化

## 规则

- 同一次运行只验证、构建一次前端，Linux/Windows 发布包复用该运行的产物。
- 普通核心集成验证与 race 验证在不同 runner 并行；审计包的 race 检查执行全部测试。
- 平台构建与后端验证并行，但开发版和标签版发布均必须等待全部验证成功。
- Go 模块缓存共享；编译缓存区分运行系统、Go 版本、目标平台及工具链版本，按运行更新并回退恢复。
- Bootlin 固定版本并按架构缓存，避免各次发布重新查询 latest。
- 已压缩发布包上传 artifact 时不重复压缩；打包使用 runner 的 pigz 并行 gzip。

## 验收场景

- 验证失败时允许构建产物留作排查，但不能写入 GitHub Release。
- 标签发布同时包含 Linux 与 Windows；主分支开发版只包含 Linux 发布包。
- 平台缓存不互相覆盖；依赖变动可回退复用既有编译缓存，工具链变更必须隔离。
- 新一轮运行可恢复上一轮同架构的编译缓存；首次运行冷缓存也能完整构建。
